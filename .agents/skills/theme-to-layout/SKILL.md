# Theme to Layout

Accept a `{brand-name}-visual-editor-theme.json` produced by [Brand to Theme](../brand-to-theme/SKILL.md), and create a sibling `defaultLayout{BrandName}.json` from the source `defaultLayout.json`, selecting the theme's colors, typography, and button/link presets. Keep the source layout unchanged. This workflow selects existing theme entries; it does not generate a new theme or install it into a site's runtime.

Example invocation:

```text
Use $theme-to-layout with /path/to/acme-visual-editor-theme.json
```

## Establish inputs

Read applicable repository instructions and the current working-tree files. Use the supplied theme path. If omitted, look for files matching `*-visual-editor-theme.json` in the repository and any output path established in the conversation; use a single unambiguous candidate, otherwise ask for the path. If only a brand guide is available, use Brand to Theme to produce the validated payload first.

Resolve paths from this `yext-standard-library` repository containing the skill, independently of the current working directory or theme file location. Write every output inside this repository. Default source: `src/library/layouts/standard-library/defaultLayout.json`. Default output: `src/library/layouts/standard-library/defaultLayout{BrandName}.json`. Honor an explicitly requested source layout or set of layouts within this repository, writing `defaultLayout{BrandName}.json` beside each source. Directory and locator layouts are separate sources; process them only when requested. Resolve relative paths from the repository root. If an output already exists, read it and preserve unrelated work; ask before replacing unrelated content.

Resolve `{BrandName}` from the brand explicitly named by the user, established in the conversation, or unambiguously identified in the supplied theme, its brand-named filename, or source brand guide. Convert it to a filename-safe PascalCase suffix: for example, Acme becomes `defaultLayoutAcme.json` and Acme Health becomes `defaultLayoutAcmeHealth.json`. The braces and `BrandName` are placeholders, not literal filename text. If the brand name cannot be determined, ask for it; a legacy generic `brand-visual-editor-theme.json` filename alone does not identify a brand. Keep brand-name metadata outside the theme payload.

Read the theme and [its payload contract](../brand-to-theme/references/payload-contract.md). Check the installed `@yext/visual-editor` definitions when they differ from that reference. Validate the saved theme using the target package's public `validateThemeData(theme, customFonts)`, passing the site’s available custom `FontRegistry` (omission checks bundled Google Fonts only): require `success === true`, parsed `data`, zero errors, and zero warnings. Typography and action fonts must exactly match values generated by `constructFontSelectOptions`; legacy shorthand may render but fails font validation. Diagnose `unsupported_font_family` using its issue path, such as `["actions", 0, "fontFamily"]`. `themeDataSchema.parse` checks structure and syntax, not font support. If validation is unavailable or fails, report the blocker before writing a branded layout; keep theme corrections in the theme-authoring workflow.

Read the entire source layout and inventory each component instance, including components under `props.content`, `props.slots`, top-level `zones`, nested card wrappers, and manual detail blocks without a component `type`. Inspect the corresponding section/slot definitions and shared atoms to determine supported styling fields and inheritance. The on-disk definitions are authoritative; do not add the same fields to every component.

**Complete when:** the theme validates, source and output paths are known, and every section and nested styling location is accounted for.

## Map theme roles

Build a working map from the layout's existing visual roles to actual theme entries. Inspect entry labels and values to understand intent; save references using exact, case-sensitive identifiers. Theme identifiers and collection sizes are arbitrary: neither `main-*` identifiers nor the payload example's identifiers are guaranteed to exist. Array order defines defaults, not heading hierarchy or action roles.

| Layout role                                                          | Selection criteria                                                                                                                                                                                                                                    |
| -------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Page, header, section, card, and footer surfaces                     | Choose an appropriate background/foreground pair for each existing role. Preserve the distinction between canvas, alternate, accent, and strong surfaces where the supplied palette supports it. Reusing a pair is valid when the palette is smaller. |
| Hero title, section heading, card heading                            | Match hierarchy using typography labels, desktop/mobile size, weight, and line height. Preserve semantic heading levels and overrides independently of visual typography.                                                                             |
| Body, caption, label, navigation, FAQ question/answer                | Choose the closest supplied typography treatment for the role. Reuse entries when the theme has fewer treatments than the layout.                                                                                                                     |
| Primary/secondary CTAs and form submission                           | Match the intended prominence, treatment, and actual surface. Use `presentation: "button"` for a visual button; a guide may specify a text CTA with `presentation: "link"`.                                                                                                                                     |
| Inline, navigation, breadcrumb, contact, read-more, and footer links | Match each role's typography, decoration, and surface using a suitable link preset. Preserve anchor behavior independently of visual presentation.                                                   |
| Icons, stars, borders, and other accents                             | Select a supported solid palette channel with suitable contrast against the actual surface.                                                                                                                                                           |

Determine the effective light/dark appearance from the resolved surrounding background, then inspect the selected action’s default, hover, and active states. Top-level states apply on light backgrounds; dark backgrounds use the complete `onDark` set when present and otherwise reuse the top-level states. Typography and button shape stay shared. Keep the same `actionId` across surfaces when its two appearances fit the role; separate presets are for distinct treatments. Nested cards may establish a different surface from their enclosing section. Match the intended treatment as well as contrast: a white filled on-color button can disappear on a white section even when its label is readable. Choose the secondary outline treatment on a light surface when that is the theme's intended role. Treat navigation as its own visual role; a body-link preset can introduce unwanted underlines, weight, or casing. If the source guide is available, use its action specimens and usage rules to resolve ambiguous labels. Otherwise use the theme's actual values and report uncertain mappings. Prefer a supplied readable action; if the theme lacks a required presentation or any readable treatment for a required role, report the specific gap and request a theme revision instead of inventing identifiers or silently editing the payload.

Trace effective action styling through the consuming component and shared atoms. Follow the payload contract’s background/action integration guidance: `Background` from `@yext/visual-editor/section-library-support` selects appearance from the resolved background, and nested backgrounds reset it. Images and gradients need an explicit `ve-theme-on-dark` or `ve-theme-on-light` class on the relevant wrapper. Verify actions retain `data-ve-action` so package CSS controls their states. Inspect copied background/action implementations and inline styles for stale surface inheritance that overrides those states, including `useActionForeground`, `CTA`, `Button`, and `HeaderLinks` when present. Ordinary text can inherit the paired foreground; actions should preserve the selected appearance’s states. Compare resulting typography, shape, colors, and feedback with the intended preset. Report copied implementations that need updating to the package behavior as runtime integration gaps; code changes remain outside this layout-only workflow.

Use the nearest surface's paired foreground for ordinary text unless the role needs an explicit override. Inspect existing literal/custom colors, inline rich-text marks, and CTA color overrides: replace presentation overrides that defeat the requested branding using supported fields, while preserving content, links, and other text formatting. Retain intentional exceptions specified by the user and report them.

**Complete when:** each section's surfaces, typography, and actions have a supported theme selection, each action's role and actual surface are accounted for, and material approximations or renderer conflicts are identified.

## Update supported selections

Re-read each source and any existing output immediately before writing and preserve unrelated working-tree changes. Copy the source layout into a separate object and apply styling selections only to that copy. Write the result to its sibling `defaultLayout{BrandName}.json`, keeping component identifiers, order, slot structure, content, entity bindings, translations, URLs, analytics, visibility, heading semantics, and migration/version metadata intact.

Use the field shapes accepted by the current components:

- Colors use `{ "colorId": "<palette-entry-id>", "channel": "background" }` or `"foreground"` at the supported color field. A surface normally selects the background channel; the pair supplies its inherited foreground. Select a channel intentionally for text/accent overrides. Gradient channels are suitable only where the consuming field supports them.
- Typography uses `typographyId` and role-specific fields such as `questionTypographyId` and `answerTypographyId`. Keep font metrics in the theme, rather than copying them into component props. Review supported legacy local font/weight fields for overrides that would prevent the chosen treatment from rendering.
- Actions use `actionId` and role-specific fields such as `readMoreActionId`. An action owns its typography, colors, border, padding, and states; select the preset instead of copying its declarations into the layout.

In this library, inspect these easy-to-miss locations when present:

- Header/footer background slots and `ExpandedFooter.props.styles.primaryFooter`.
- `HeaderLinks`, contact/address/email links, social links, linked images, and nested CTA slots.
- `FooterLinksSlot.props.actionId`, which lives outside `styles`.
- `FormSection.props.ctaStyles.actionId` for the submit action.
- FAQ question/answer typography and About/Reviews read-more actions.
- Hero review stars, gallery accents, phone icon backgrounds, and nested nearby-location heading/contact styles.
- Locator/directory results, filters, and card slots when those layouts were requested.

Add supported explicit selections where a component otherwise falls back to an unsuitable first collection entry. Components with no applicable styling field can inherit; account for that inheritance rather than inventing props. Check parent-controlled styling and resolved child defaults when a saved selection appears to have no effect.

Keep scope to the requested color, typography, and action treatments. Preserve spacing, sizes, image/card geometry, and layout variants unless the user also requests those changes. Serialize the branded output using the source layout's formatting and a trailing newline. Keep the source layout and theme unchanged. Leave layout registration and imports unchanged unless separately requested.

## Verify and report

Read back and parse each saved layout. Recursively inspect all theme selection fields, including role-specific `*TypographyId` and `*ActionId` fields and color objects. Require every selected identifier to exist in the matching input collection, every channel to be compatible with its consumer, and every action's presentation to fit its visual role. Check effective inherited/default selections as well as explicit references; runtime fallback must not conceal unresolved references.

Compare each branded output against its source, allowing only the intended styling differences. Verify that the source layout and theme bytes remain unchanged. Ensure every inventoried section is covered, including nested surfaces and explicit custom overrides. Run the repository's applicable checks (normally `npm run typecheck` and `npm run validate`); report failures accurately, distinguishing existing issues when evidence supports that distinction. Follow repository build/test requirements if committing.

When a local preview is available, render the branded output with the supplied payload active through the existing theme integration, using a temporary preview setup if needed without changing committed imports or registration. Compare desktop and mobile buttons/links against the source guide when available, including header/footer, light and dark surfaces, nested backgrounds that reset appearance, and image/gradient wrappers with explicit appearance. Verify both `onDark` states and the top-level fallback where `onDark` is absent. Inspect default, hover, and active states, checking computed typography, loaded fonts, decoration, fill, text/border colors, padding, and corners. Confirm the primary/secondary hierarchy remains visible on the actual surfaces and that navigation retains its intended treatment. Record any mismatch caused by runtime overrides separately from a theme or mapping defect. Setting layout references alone does not activate the source theme. If preview or theme activation is unavailable, report visual verification as incomplete rather than claiming the appearance was verified. Do not modify runtime integration merely to complete this workflow.

**Complete when:** each `defaultLayout{BrandName}.json` exists inside this repository, all saved selections resolve against the input theme, source files are unchanged, content and structure are preserved, each section is accounted for, and check/preview results are recorded. Return clickable absolute paths to the branded outputs, a brief account of the role mappings, and any approximations, inherited treatments, or verification limits. Remind the user that the same payload must be active at runtime if that has not been verified.
